# MRL 8차 개발 결과 — 2026-09-28

요청한 다섯 작업을 격리된 MRL 작업 공간에서 구현했다. GPT-5.6 Terra 세 작업자가 컴파일러, 지식 처리, 값/수치 처리를 병렬로 맡았고, 통합 과정에서 소유권·힙 저장·실제 증분 계산을 보완했다. 전체 **131개 검사 통과**, 실패·오류·건너뜀 0개다. 이번 결과는 실험용 언어 구현이며 마르코 본체에 배포한 결과는 아니다.

## 구현 결과

| 작업 | 이번에 동작하는 범위 |
| --- | --- |
| 지식 용량 확대 | 소스에서 `Horn(capacity=64..16384, ...)`; 기본값 64. 선택한 용량에 맞춘 힙 저장 |
| 외부 지식 입력 | 실행 중 UTF-8 JSONL 파일 읽기. `plan.load(path)`가 `Result<si32,s>` 반환. 재컴파일 불필요 |
| 함수 인자·반환 | `Horn`, `Snapshot` 전달·반환. Horn은 복사 후 수정 시 분리, 기존 스냅샷은 유지 |
| 기본 자료형 | `arr<si32,N>`, `arr<f32,N>`, `list<si32>`, `list<f32>`, 기본형을 담는 `Result<T,E>` |
| 수치·증분 처리 | 검사된 f32 연산과 `sum`/`dot`/`norm`/`cosine`; 제한된 규칙에서 추가된 사실만 새로 규칙 계산 |

새 기능은 IR v6를 사용한다. 기존 IR v2–v5 경로는 유지하며, 원시 IR 입력도 백엔드에서 독립적으로 검증한다. 타입을 함수 선언에서만 사용한 경우도 v6로 선택한다.

## 값과 메모리

- 고정 배열은 길이 1..16384의 값이다. 목록은 참조를 공유한다. 목록 별칭에서 `push`하면 다른 별칭에서도 보인다. 둘 다 `.len`과 범위를 검사하는 인덱스 읽기를 지원한다.
- `Result<T,E>`의 두 타입은 각각 `si32`, `f32`, `s`, `b` 중 하나다. 타입 문맥 안에서 `Ok`/`Err`를 만들고 `match`로 분기한다. 중첩 Result나 관리되는 목록/Horn을 Result 안에 넣는 기능은 없다.
- f32는 유한한 값과 범위를 검사한다. 수치 커널은 `list<f32>` 대상이며 차원 불일치, 0으로 나누는 코사인, NaN/overflow 등을 거부한다.
- Horn은 참조를 공유하다 수정할 때 분리한다. 목록과 Horn의 복사 의미가 다르다. 함수 인자/반환, 임시 값, 대입, 조기 반환에서 소유권을 정리한다.
- 스냅샷은 캡처한 계획과 계산 결과를 보유한다. 같은 스냅샷을 다시 출력할 때 추론을 재실행하지 않는다. 스냅샷을 계속 보관하면 그만큼 메모리를 사용한다.
- 반복된 목록 연산과 200회 스냅샷 질의/수정 검사에서 관리 대상 할당이 마지막 해제 후 0개임을 확인했다. 기존 정적 질의의 프로그램 수명 캐시는 별도 동작이다.

## 외부 파일 형식

한 줄에 JSON 객체 하나다. 빈 줄과 마지막 줄의 줄바꿈 생략을 허용한다.

```json
{"id":"fact-1","triple":["marco","learns","graphs"]}
{"id":"fact-2","subject":"marco","predicate":"reads","object":"책","polarity":true,"modality":"asserted","evidence":{"source":"책 읽기","start":0,"end":1,"text":"책"}}
```

`id`와 삼중항은 필수인 비어 있지 않은 문자열이다. `triple`과 `subject`/`predicate`/`object` 표현을 섞을 수 없다. polarity 기본값은 true, modality 기본값은 asserted이며 asserted/planned/conditional만 허용한다. Evidence는 생략, 빈 객체, 또는 source/start/end/text 전체를 받는다. 위치는 UTF-8 바이트 위치가 아닌 Unicode 문자 위치이며 `[start,end)` 부분 문자열이 text와 같아야 한다.

중복 키, 알 수 없는 키, 파일 내부 또는 기존 계획과 겹치는 ID, 잘못된 JSON/UTF-8/서로게이트/NUL, 잘못된 Evidence, 용량 초과를 거부한다. 파일 크기 상한은 **32 MiB**, 레코드 수는 계획의 남은 용량이다. 개별 줄에도 이 전체 바이트 상한이 적용된다. Windows의 한글·이모지 파일 이름도 확인했다.

파일 전체를 검증한 뒤 한 번에 적용한다. 실패는 `Err(message)`이며 사실과 버전이 바뀌지 않는다. 성공은 `Ok(추가 수)`이며 비어 있지 않은 배치마다 버전이 한 번 증가한다. 빈 배치는 `Ok(0)`이고 버전을 바꾸지 않는다. 메모리 할당 실패 등 일반 런타임의 치명적 오류까지 복구 가능한 Result로 바꾼 것은 아니다.

## 지식이 늘어날 때의 동작과 한계

증분 경로는 **긍정·asserted 사실의 뒤쪽 추가**, **술어가 상수인 단일 전제 규칙**, **규칙 결과가 다른 규칙 입력으로 이어지지 않는 경우**의 `closure`에 적용한다. 이미 계산한 사실/규칙 조합의 결론을 보존하고, 새로 들어온 고유 사실에 대해서만 바인딩과 결론 계산을 수행한다. 같은 사실의 Evidence 변경도 기존 전체 계산과 같은 결과를 낸다.

삭제, 입력 앞부분 변경, 규칙 변경, 부정 사실, provenance, 재귀·연쇄 규칙, 변수 술어 및 빠른 경로에서 예산/용량을 넘기는 경우에는 기존 전체 평가기로 돌아간다. 결과 순서, 선택된 근거, 부모 링크, 예산 의미를 유지하는 것이 우선이다.

**모든 비용이 추가된 사실 수에만 비례하는 것은 아니다.** 입력 검증·인코딩과 전체 결과 구성은 기존 사실도 다룬다. 스냅샷/별칭이 유지된 Horn을 수정하면 문자열까지 복사할 수 있다. 파일 ID 중복 검사는 현재 최대 16,384건으로 제한된 선형 비교를 반복하므로 최악 O(N²)이다. 큰 파일의 반복 적재에서 병목으로 확인되면 ID 색인으로 바꿀 지점이다. 이번 작업으로 마르코의 전체 지식 증가·오버레이 문제를 해결했다고 해석하면 안 된다.

### 지식 추가: 기존 native 전체 계산과 비교

| 시작 사실 수 / 매회 추가 | 전체 계산 | 증분 계산 | 시간 비율 |
| --- | ---: | ---: | ---: |
| 64 / +1 | 0.0047 ms | 0.0020 ms | 2.35배 |
| 512 / +8 | 0.0367 ms | 0.0085 ms | 4.32배 |

마지막 행의 최종 질의는 5,056개 입력 중 **기존 4,992개 결론 재사용, 새 64개 규칙 계산**이었다. 모든 질의에서 전체 wire 결과가 기존 평가기와 바이트 단위로 같았다. p95는 전체 1.0498 ms, 증분 0.2353 ms였다.

상주 native 커널과 ctypes 호출, 전체 wire 결과 생성까지 포함한 비교다. **파일 읽기, 문자열 인코딩/인터닝, 소스 컴파일, 프로세스 시작은 제외**한다. Python 대비 속도도 아니다. JSON의 cold 항목은 이미 로드된 라이브러리의 첫 질의이며 프로세스 최초 실행 시간이 아니다.

### 수치 연산: Python과 비교

길이 4,096인 목록 두 개를 새로운 값으로 생성하고 sum/dot/norm을 계산했다. native는 C 값 런타임을 직접 사용했으며, `.mrl` 컴파일러 전체의 성능을 측정한 것은 아니다. Python은 f64 누산을 사용하므로 최종 수치의 오차 허용치 0.02 안에서 비교했다.

| 구간 | Native | Python |
| --- | ---: | ---: |
| 상주 계산 중앙값 | 0.0254 ms | 0.5998 ms |
| 프로세스 실행 전체 중앙값 | 204.2770 ms | 248.4765 ms |
| 프로세스 실행 전체 p95 | 340.7568 ms | 288.1431 ms |

작은 수치 커널의 상주 계산은 이 실험에서 약 23.6배 빨랐다. 프로세스 시작을 포함하면 차이가 작아지고 native의 p95는 오히려 느렸다. 컴파일 시간은 표에서 제외했다. 목록 자체의 데이터/헤더 합계 32,848바이트는 프로세스 전체 메모리 수치가 아니다. 모든 프로그램이 Python보다 빠르다고 주장할 근거는 없다.
