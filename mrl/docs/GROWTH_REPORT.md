# MRL 그래프 성장 성능 측정과 수정

2026-09-28. 분리된 `codex/mrl-runtime-language` 작업본의 네이티브 추론 런타임을 측정했다. 원래 Marco 엔진과 Python oracle은 수정하지 않았다. 아래 수치는 최종 JSON 기준이며, 작업 도중 안내한 예비 측정과 구분한다.

## 수정한 부분

- Windows OS 버전 조회에서 발생하던 외부 명령 실행과, 이미 준비된 Zig를 찾기 전 불필요한 PATH 검색을 제거했다. 빌드 캐시는 소스·컴파일러·플랫폼을 계속 확인한다.
- 사실 및 부정 사실은 해시로 조회하고, 후보 색인은 순서를 보존하는 연결 목록으로 구성했다. 기존 용량 제곱 크기의 색인 공간을 선형 크기의 힙 공간으로 바꿨다.
- `PreparedGraph(case, capacity=N)`으로 64..16384 사실 저장 공간을 명시할 수 있다. 추론 예산은 별도이며 기본값, 기존 byte/CLI 및 .mrl 소스 Horn의 64개 제한은 유지한다.
- 근거용 임시 버퍼는 proof_limit(최대128)과 사실별 입력 근거 최대 개수에 맞춰 잡는다. 이번 capacity8192/proof_limit8 사례에서 32MiB 대신 2MiB를 할당한다. 입력 근거가 많은 사실이 있으면 더 큰 공간이 필요할 수 있다.
- 결과 캐시는 추가하지 않았다. 추가 후 평가에서 최신 입력으로 추론과 근거를 다시 계산한다. 정확한 결과·근거 순서·검색 횟수·예산·실패한 추가의 원자성을 유지한다.

## 첫 실행: 64개 사실 반환

동일한 3개 규칙 연쇄, 16개 입력 사실로 총64개 사실을 반환한다. 실행 파일/DLL은 미리 빌드되어 있다. OS 파일 캐시를 비운 측정은 아니며, 일회성 컴파일 비용은 별도 기록했다.

| 작업 | 수정 전 프로세스 전체 | 수정 후 프로세스 전체 | 같은 회차 Python | 수정 전 내부 첫 결과 | 수정 후 내부 첫 결과 |
|---|---:|---:|---:|---:|---:|
| 일반 추론 | 632.899ms | 352.785ms | 336.189ms | 373.062ms | 17.814ms |
| 근거 포함 추론 | 503.721ms | 354.617ms | 335.325ms | 299.291ms | 22.088ms |

프로세스 전체는 부모에서 프로세스 생성부터 종료·결과 회수까지 잰 시간이며 측정 도구 로딩, JSON 직렬화와 IPC가 포함된다. 내부 첫 결과는 런타임 import·초기화부터 결과 객체 생성까지로, 인터프리터 기동과 측정 도구 자체 로딩은 제외한다. 두 시간을 섞어서 시작 비용이라고 해석하지 않는다. 작은 입력에서 전체 실행 시간이 항상 Python보다 짧아진 것은 아니다.

## 사실 추가 후 최신 결과 반환

각 목표 크기의 바로 전 상태를 준비한 뒤 새로운 사실 1개를 추가하고, 모든 결론/근거 결과를 반환하는 시간을 25회 측정했다. 입력 추가와 평가를 양쪽 모두 포함하며, 정답 비교와 JSON 직렬화는 타이머 밖에 둔다. 총 사실 수는 입력 사실 + 파생 사실이다. 일반 추론/근거 포함 모두 3규칙 연쇄로,256/1024/4096개 총 사실은 각각64/256/1024개의 입력 사실에서 나온다.

| 작업 | 총 사실 | MRL 중앙값 | Python 중앙값 | Python / MRL | MRL p95 | MRL 최대 메모리 중앙값 | Python 최대 메모리 중앙값 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 일반 추론 | 256 | 2.387ms | 3.978ms | 1.67배 | 5.371ms | 22.14MiB | 20.93MiB |
| 일반 추론 | 1,024 | 6.667ms | 14.569ms | 2.19배 | 8.489ms | 22.42MiB | 22.24MiB |
| 일반 추론 | 4,096 | 28.271ms | 85.740ms | 3.03배 | 65.181ms | 26.41MiB | 27.21MiB |
| 근거 포함 추론 | 256 | 5.220ms | 11.289ms | 2.16배 | 12.026ms | 24.54MiB | 21.58MiB |
| 근거 포함 추론 | 1,024 | 17.888ms | 45.089ms | 2.52배 | 29.713ms | 26.25MiB | 24.58MiB |
| 근거 포함 추론 | 4,096 | 99.520ms | 234.859ms | 2.36배 | 174.327ms | 35.53MiB | 36.25MiB |

4,096개 사실의 근거 포함 사례에서 프로세스 최대 메모리 중앙값은 임시 버퍼 수정 전 41.63MiB에서 최종 35.53MiB로 줄었다. 메모리는 Windows PeakWorkingSetSize로, 별도 새 프로세스의 런타임 및 결과 객체까지 포함하며 결과 JSON 직렬화 전에 읽었다. 그래프 단독 메모리나 가상 메모리 예약량은 아니다.

그래프가 커질수록 시간이 늘어나는 현상은 남아 있다. 전체 추론과 전체 결과 반환을 수행하므로 상수 시간 갱신이나 증분 추론을 달성한 것은 아니다. 회차 간 Python 측정값도 변하고 p95가 중앙값보다 상당히 크므로, 작은 전후 차이를 확정적인 속도 개선/퇴보로 해석하지 않는다. 특히 메모리 수정 자체가 실행 시간까지 줄였다고 주장하지 않는다. 각 회차 안의 Python 비교와 원시 표본을 함께 확인해야 한다.

## 검증 및 한계

- 전체 테스트 101개 통과, 실패/오류/건너뜀 0개. 검사 시간 38.59초.
- 모든 최종 측정 사례에서 전체 구조가 oracle과 일치하며 완전한 결과와 실제 사실 수를 검사한다. 용량 초과 추가가 기존 상태를 바꾸지 않는 것도 확인한다.
- 단일 전제 규칙 32개, 사실별 근거128개 등의 한계는 유지한다. 다중 전제 결합, 일반 증분 추론, .mrl 소스의 동적 Horn 계획은 이번 수정에 포함하지 않는다.
- 4,096개 사실까지 정식 측정했다. 별도 기능 확인에서 8,192개 결과의 일치도 확인했지만, 수십만~수백만 그래프나 실제 모델 문장 생성 성능을 입증한 것은 아니다.
- 첫 실행 표본은 기본 용량7회, 확장 용량5회이며 p95는 작은 표본의 nearest-rank 값이다. 입력 추가는25회씩 측정했다. 컴파일러 캐시가 이미 따뜻할 수 있는 일회성 빌드 시간은 JSON에 별도 기록한다.

## 재현

분리된 작업본 루트에서 실행한다. `--snapshot`은 무시되는 `.build/growth-baseline-snapshot`의 원본을 사용하며 원본 비교 결과를 다시 쓸 수 있으므로 출력 파일을 명시한다.

```powershell
python -B -m unittest discover -s mrl/tests -v
python -B -m mrl.benchmark_growth --output mrl/docs/GROWTH_AFTER.json --samples 7 --warm-samples 25 --append-samples 25 --append-endpoint-only
python -B -m mrl.benchmark_growth --output mrl/docs/GROWTH_SCALE.json --capacity 8192 --sizes 64,256,1024 --samples 5 --warm-samples 25 --append-samples 25 --append-endpoint-only
```

[수정 전](GROWTH_BASELINE.json) · [수정 후](GROWTH_AFTER.json) · [확장 측정](GROWTH_SCALE.json) · [검증](GROWTH_VERIFICATION.json). `*_INTERIM.json`은 근거 버퍼 수정 전 자료이며 최종 결과가 아니다. 최종 JSON의 native_graph.c/native_graph.py/toolchain.py/benchmark_growth.py 해시는 측정에 사용한 파일과 일치한다.
