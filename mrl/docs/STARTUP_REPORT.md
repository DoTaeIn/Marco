# MRL 시작 비용 개선

기존 Marco와 분리된 `C:/Users/hirob/.codex/worktrees/mrl-runtime/Marco/mrl/`에서 작업했다. GPT-5.6 Terra 작업자들은 저장소·내용 식별·회귀 검증을 맡았고, 주 작업에서 측정과 통합을 수행했다. Marco 본체에는 병합하지 않았다.

## 프로세스 시작부터 첫 정답까지

동일한 입력과 규칙으로 변경 전/후 런타임을 다시 빌드해 번갈아 측정했다. 각 경우 새 native C 프로세스를 띄우고, 정확한 결과 수를 확인한 뒤 부모가 응답을 받는 시점까지 포함한다. 문자열 입력 N건에 `p → q` 규칙을 적용하므로 결과는 2N건이다. 5회 중앙값이며, OS 파일 캐시는 비우지 않았다. 컴파일과 입력 파일 생성은 제외했다. 첫 질의만 따로 잰 시간을 시작 시간으로 사용하지 않았다.

| 입력 사실 | 변경 전 | 개선 후 | 시간 감소 | 속도비 |
|---|---:|---:|---:|---:|
| 10,000 | 285.10 ms | 262.96 ms | 7.8% | 1.08배 |
| 100,000 | 494.05 ms | 381.02 ms | 22.9% | 1.30배 |
| 1,000,000 | 2,993.38 ms | 1,598.65 ms | 46.6% | 1.87배 |

빈 프로그램을 띄워 즉시 응답하는 대조 실행도 중앙값 약 282 / 258 ms(전/후)가 걸렸다. 작은 데이터의 전체 시작 시간에는 실행 환경 변동이 크므로 이번 5회 표본으로 전부 빨라졌다고 주장하지 않는다. 전체 시간에서 실제 복원 함수만 나누어 보면 다음과 같다.

| 입력 사실 | 전: 내부 복원 | 후: 내부 복원 |
|---|---:|---:|
| 10,000 | 29.65 ms | 18.88 ms |
| 100,000 | 244.61 ms | 123.28 ms |
| 1,000,000 | 2720.12 ms | 1395.30 ms |

이전 9차 기록의 100만 건 2.75초는 당시의 별도 측정이다. 이번 표는 현재 환경에서 변경 전 코드와 개선 후 코드를 같은 경계로 재측정한 비교다. 다른 프로그램의 부하와 파일 캐시 상태는 지연에 영향을 줄 수 있다.

## 지식이 늘어나는 경우

기본 체크포인트를 만든 뒤 입력의 1%를 추가하고 변경 기록만 commit했다. 전체 준비 캐시를 다시 저장하지 않은 채 새 프로세스로 재시작했다. 모든 경우 캐시 적중과 정확한 2(N+추가분) 결과를 확인했다.

| 기본 + 추가 사실 | 전: 재시작→첫 정답 | 후: 재시작→첫 정답 | 후: 복원 뒤 증분 질의만 | 후: 추가 전체+디스크 commit |
|---|---:|---:|---:|---:|
| 10,000 + 100 | 263.14 ms | 257.54 ms | 0.031 ms | 1.039 ms |
| 100,000 + 1,000 | 498.60 ms | 371.97 ms | 0.454 ms | 3.493 ms |
| 1,000,000 + 10,000 | 2,994.95 ms | 1,637.21 ms | 5.571 ms | 8.390 ms |

마지막 두 열은 재시작 총시간이 아니다. 추가+commit은 해당 행의 추가분 전체를 한 번에 처리한 시간이다. 재시작에 쓰인 체크포인트/캐시는 commit 이전 세대이므로 이 측정은 변경 로그를 반영하는 경로도 포함한다.

## 수정한 병목

- 복원 시 문자열 색인을 한 번 예약하고, 문자열과 ID 행을 예산 안의 블록에 묶어 저장한다. 임시 문자열 버퍼도 재사용한다. 이후 추가 문자열은 기존 경로로 기록하며 스냅샷 공유·실패 시 되돌리기를 보존한다.
- 작은 필드를 64 KiB 읽기 버퍼로 묶고 43바이트 체크포인트 행을 한 번에 처리한다. CRC32는 동일한 IEEE 다항식을 네 바이트씩 처리한다. JSONL의 두 입력 경로도 공용 묶음 읽기를 사용해 최초 입력에서 문자마다 파일 함수를 호출하던 비용을 줄였다.
- 같은 저장소의 전체 내용 해시를 캐시 검증과 저널 세대 이름에 재사용한다. 규칙 초기화가 문자열을 추가한 경우에는 새 내용을 다시 해시한다. 외부 캐시 호출은 여전히 스스로 전체 식별을 검증한다.

저장 스키마, 바이트 순서, CRC, 문자열/행 검증, 캐시 내용·규칙 식별, 증명 DAG 검사, 예산 거부와 손상 시 원본 보존은 유지했다. 예전 코드가 기록한 체크포인트를 그대로 읽는다. 독립적으로 구성한 이전 형식 파일도 읽고 바이트 단위로 동일하게 다시 저장하는 검사를 통과했다.

1,000,000건 복원에서 추적 최대 메모리는 1.188 GB → 1.093 GB였다. 이는 전체 프로세스 RSS가 아니다. 저장소·엔진·공유 스냅샷의 추적 할당은 1.5 GiB 예산에 포함하며, 파일 스트림당 고정 64 KiB 스택 버퍼와 C 런타임 메모리 등은 밖에 있다.

## 남아 있는 시작 비용

최초 JSONL 입력부터 첫 정답까지는 1,000,000건 기준 3.119초 → 2.659초였다. 위의 준비된 체크포인트 복원과는 별도 경로이며, 최초 입력·전체 추론 비용도 원시 기록에 포함했다.

파일을 읽고 검증하며 색인을 만드는 작업은 여전히 지식 크기에 따라 증가한다. 즉시 시작 또는 크기와 무관한 시작 시간을 구현한 것은 아니다. 이번 변경은 전체 파일을 검사하는 의미를 유지하면서 중복 해시·반복 읽기·할당 비용을 줄였다. 디스크 캐시를 강제로 비운 콜드 부팅 수치, 복잡한 모든 규칙에 대한 속도비, Python 대비 보편적 우위는 이 측정으로 주장하지 않는다.
