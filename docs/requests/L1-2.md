# L1-2: what the realizer needs from the why chain to say "why" in words

From: goal L1 (trace ledger core), branch `trace-ledger`.
For: the owner of `marco/language/` (goal W3 and after). L1 does not own it and
composes no sentence: `marco/trace/why.py` returns events, `pretty.py` puts
field values side by side.

## The chain L1 provides

`marco.trace.why.Graph(ledger).chain(output_id)` returns, in ledger order,
every event an `output_created` rests on along `parent_ids`;
`Graph.inputs(output_id)` returns only its `input_received` events. On the
seven-step dialogue the answer after the restart rests on turns 1, 2, 5 and 9:
the two statements, the correction, and the question
(`tests/trace/test_trace_turns.py::test_the_why_chain_reaches_the_inputs_an_output_rests_on`).

What a chain holds today, per event kind:

| Kind | Fields a sentence could use |
| --- | --- |
| `input_received` | `payload.turn`, `payload.text` (what the user said), `payload.sha256` |
| `observation_created` | `payload.index`: the statement the engine stored |
| `state_changed` | `subject`, `payload.field`, `before`, `after`, `delta`, `operation.type` (`state_update`, `quantity_update`, `correction`), `supersedes` |
| `conclusion_withdrawn` | `payload.withdrawn`, `superseded_by`, `reason` (`corrected`, `recomputed_after_correction`, `not_in_replay_after_correction`) |
| `rule_applied` | `operation.id` (the operator), `operation.rules` (rule ids, when the meaning names them) |
| `conclusion_created` | `payload.fact` `[subject, relation, value]`, or `kind: explanation` |
| `hold` | `status` (`hold`, `refused`), `payload.reason`, `payload.missing` (subject, relation, candidates, word, said) |
| `hypothesis_verified` / `hypothesis_rejected` / `contradiction_found` | `payload.checks` reasons |

## Request

1. **An explain plan that reads a chain.** Declare in `meaning.json` an
   explain meaning built from a chain (`act: explain`, `kind: chain`) with
   roles for: the conclusion (`fact`), the state changes in order (subject,
   before, after, the rule id that made each), the statements they rest on
   (by turn, quoted from `input_received.payload.text`), and a correction
   (`conclusion_withdrawn` with `superseded_by`) as "after the correction".
   Then "why" can be answered from the trace graph (design note §15, §44
   principle 6) rather than from `ReasoningContext._explain_last`'s own
   meaning. The chain has no rule id per state change until L1-1 B3 lands;
   until then `operation.rules` on the operator event is all there is.
2. **A hold explained from its chain.** A held reply's chain ends in a `hold`
   event whose `missing.said` names an earlier `input_received` when the hold
   waits on an unread statement (9 of the 12 held answerable turns on the
   round-3 dev set). A frame for "I could not read what you said at turn N,
   so I cannot answer this" would use it.
3. **The meaning's reason in the report.** `realize_with_report` keeps the
   turn's `meaning.reason` and `meaning.act` in its report (`report["meaning"]
   = {"act", "reason"}`), and the matched `turn_plans` entry by key. Then
   `output_created` can carry what was held and why even when the caller has
   no engine meaning.
4. **A declared version.** A `version` field in
   `marco/language/realizer/<stem>.json` and `meaning.json`. The trace stamps
   the realizer by file digest today (`runtime.realizer.sha256`); a version
   says whether two digests are the same declarations released twice.
5. **Rejected expressions as events, later.** The report already lists each
   clause's `attempts` with the checker's failures. Emitting them as
   `hypothesis_rejected` (candidate id, failures) when a ledger is on would
   answer "why did you say it this way". Not needed for the gate.
