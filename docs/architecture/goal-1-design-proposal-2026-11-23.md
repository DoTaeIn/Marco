## 0.2 개정 2: 확정된 결정과 첫 단계 구현 (2026-11-23)

**기획 기준으로 확정된 것.** F.5의 해당 행에도 표시했다.

| 항목 | 결정 |
| --- | --- |
| 연산 목록 | 목표 범위는 O1~O9. 첫 단계는 구조 입력의 조회·관계 결합·주장 확인 |
| 상태 | 11개 구분 채택. `unverified`와 `verification_failed`는 모두 수용 시험 미통과 |
| 구현 위치 | `origin/weight_test`에서 분기한 새 브랜치. 본체에 구현하지 않는다 |
| 자연어 범위 | 의미 틀 10개와 그 조합이 초기 필수 범위. 특정 문장 목록으로 줄이지 않는다 |
| 자연어 지식 입력 | 최종 수용에 포함. 첫 단계의 구조 입력 성공은 중간 성과다 |

**바로잡은 두 가지.**

1. **검증 결과가 최종 판정이다 (B.3, B.6).** 단일 우선순위표를 없앴다. 추론기가 먼저 추론 상태를 내고, 확인 절차의 결과로 최종 상태를 정한다. 거절이면 추론 상태가 무엇이든 `verification_failed`다(답이 없다는 결과 포함). 일치는 추론 상태를 그대로 둘 뿐 `no_knowledge`나 `ambiguous_entity`를 `answered`로 바꾸지 않는다.
2. **첫 단계가 쓰지 못하는 지식은 드러내고 막는다 (E.1).** 같은 진술의 긍정·부정, `single` 관계의 상충 값은 `conflict`로 막는다. 적용 기간·적용 조건·승계가 붙은 진술, 모든 규칙, 모든 변경 기록은 "쓸 수 없음"으로 보고하고, 그것에 닿는 질문은 `out_of_scope`다. 한정어를 떼고 사실로 쓰는 길은 없다.

**새로 적은 약점에 대한 검토 판단.**

- 전수 열거 비용: 첫 단계의 작은 지식에서 검증용으로 쓴다. 한도 초과율을 재고, 목표 규모에서 반복해 실패하면 방법을 바꾼다.
- 같은 작성자의 두 구현: 인정하는 한계다. 두 구현의 일치는 내부 교차검사이며 독립 평가를 대신하지 않는다.
- 기록 시간이 순번인 점: 날짜로 된 기록 시점 질의는 **미지원**이다. 적용 날짜 질의(`at`)와 구분한다.
- **보류.** 파생 충돌을 표시하고 처음부터 다시 적용하는 방식(B.2의 6)은 의미적 정확성이 입증되지 않았다. 순환·예외와 결합하면 정당한 결론까지 막을 수 있다. 규칙 구현 단계 전에 따로 검토하며, 그 전에는 확정된 설계가 아니다.

**구현 결과는 E.2에 있다.**

## 1. 한 장 요약

1. **구조는 하나다: 조건이 붙은 진술.** 사실은 `(주어, 관계, 값)`에 참·거짓, 유효 기간, 적용 조건, 출처, 기록 순번이 붙은 진술이다. 규칙은 변수가 든 진술이고, 질문은 빈칸이 든 진술이다. 개체·단위·관계 선언은 기존 어휘 팩에, 진술·규칙·변경은 기존 사실 팩에 넣는다. 새 저장소나 새 VM은 제안하지 않는다.
2. **파생 결론은 저장하지 않는다.** 질문마다 유효한 진술에서 다시 계산한다. 그래서 수정·철회가 결론에 자동 반영되고, 진리 유지 장치가 필요 없다.
3. **참·거짓·모름·충돌을 구분한다.** 근거 있는 거짓, 근거 없는 모름, 닫힌 관계로 선언된 부재, 참과 거짓의 근거가 함께 있는 충돌을 다르게 다룬다. 예외 조건이 모름이면 결론을 확정하지 않고 그 조건을 묻는다. 충돌한 전제에서는 아무것도 파생하지 않는다.
4. **결과 상태는 11개**이고 기존 `answer.py`의 `answered`/`hold`+사유 문자열을 세분한 것이다. 부분 해석·느슨한 이름 대조·검사하지 못한 답은 `unverified`(후보)로만 나가고, 확인 절차가 거절한 답은 `verification_failed`로 막힌다.
5. **자연어와 구조 입력은 질문 그래프에서 만난다.** 그 뒤의 추론·검증은 언어를 모른다. 이 경계는 기존 `answer`(본문) / `answer_graph`(그래프) 두 입구를 그대로 잇는다.
6. **첫 구현 단계는 구조 입력만으로 조회·개체 식별·복수 정답·부정·모름·근거를 끝내는 것**이다. 파일 3개, 자연어 변경 없음.
7. **가장 큰 미해결은 자연어 범위다.** 현재 reader가 읽는 문형은 두 가족뿐이다. 조건·예외·시간·수량이 든 질문을 읽게 하는 일은 6단계로 분리했고, 범위 축소가 필요하면 F절의 제안처럼 원래 목표와의 차이를 적어 검토받는다.

## A. 최소 의미 구조

### A.1 선택: 조건이 붙은 진술 하나

기존 교사 스키마(`graph_example_acquisition/SCHEMA.md`)는 사실 하나를 `relation` 노드 하나와 간선(`kind` 리터럴, `subject`, `amount`)으로 이미 실체화한다. 사건의 `polarity`도 그 노드의 리터럴 간선이다. 즉 "진술 노드에 간선을 더 붙인다"는 방식은 새 구조가 아니라 **지금 구조의 연장**이다. 그래서 아래 다섯 가지만 더한다.

| 더하는 것 | 이유 | 지금 상태 |
| --- | --- | --- |
| 개체 기록(식별자·이름 여럿) | 이름이 아니라 식별자로 동일성을 판정한다 (G3) | 이름 문자열 비교, 별칭 표 `aliases` |
| 형식 있는 값(수+단위, 날짜, 구간, 글, 개체 참조) | 비교·계산·단위 보존 (G4, G6) | `"14일"` 같은 불투명 문자열 |
| 진술 한정어: `holds`, `valid`, `where`, `source`, `recorded` | 부정·시간·적용 조건·출처·이력 (G5, G7, G8, G10) | `source{url, as_of, scope}`만 있고 실행에 쓰이지 않음 |
| 규칙(`if`/`test`/`then`/`overrides`) | 조건·예외·연쇄·계산 (G5, G6) | 없음 |
| 변경 기록(`supersedes`, `retracts`, `corrects`) | 날짜별 변경·철회·정정 (G8) | 단어 기억의 `forget`만 있음 |

세 팩 구분은 유지한다. 분야를 바꿀 때 바뀌는 것은 어휘 팩과 사실 팩뿐이다(G11).

### A.2 기록 형식 (제안: 어휘 팩 `graph-field-words-v2`, 사실 팩 `graph-field-facts-v2`)

가상 분야 "모래섬 해운"으로 보인다. 전부 지어낸 자료다.

어휘 팩 — 분야의 말, 개체, 관계의 성질, 단위:

```json
{"schema": "graph-field-words-v2", "field": "가상 여객선",
 "things": [
  {"id": "t.sand", "type": "배", "names": ["모래섬호", "1호선"]},
  {"id": "t.big",  "type": "배", "names": ["큰등대호", "등대호"]},
  {"id": "t.small","type": "배", "names": ["작은등대호", "등대호"]},
  {"id": "t.east", "type": "항구", "names": ["동쪽항"]}],
 "relations": [
  {"p": "정원",   "value": "quantity", "single": true},
  {"p": "출발항", "value": "thing",    "single": true},
  {"p": "섬주민", "value": "truth",    "absent_means": "unknown"},
  {"p": "자전거적재", "value": "truth", "absent_means": "unknown"}],
 "units": [{"unit": "g", "base": "kg", "per_base": "1000"}]}
```

- `names`는 다대다다. 한 이름이 두 개체에 걸리면 그 이름은 애매하다(위의 `등대호`).
- `single: true`는 같은 주어·같은 조건·같은 시점에 값이 하나여야 한다는 선언이다. 충돌 판정에 쓴다. 선언이 없으면 값 여럿은 복수 정답이다.
- `absent_means`는 `unknown`(기본) 또는 `false`다. `false`는 "이 관계는 목록이 완전하므로 없으면 거짓"이라는 분야의 선언이고, 그 가정을 쓴 답에는 가정이 표시된다.

사실 팩 — 진술, 규칙, 변경:

```json
{"schema": "graph-field-facts-v2",
 "statements": [
  {"id": "K01", "s": "t.sand", "p": "정원", "o": {"n": "120", "unit": "명"},
   "valid": ["2026-01-01", null], "source": {"doc": "운항 안내 3쪽", "as_of": "2026-11-01"}, "recorded": 1},
  {"id": "K02", "s": "t.sand", "p": "출발항", "o": {"thing": "t.east"}, "source": {"doc": "운항 안내 1쪽"}, "recorded": 2},
  {"id": "K03", "s": "t.sand", "p": "자전거적재", "holds": false, "source": {"doc": "수하물 규정 2조"}, "recorded": 3},
  {"id": "K04", "s": "t.sand", "p": "첫출항", "o": {"time": "07:00"}, "where": {"요일구분": "평일"}, "source": {"doc": "시간표"}, "recorded": 4},
  {"id": "K05", "s": "t.sand", "p": "첫출항", "o": {"time": "08:30"}, "where": {"요일구분": "주말"}, "source": {"doc": "시간표"}, "recorded": 5}],
 "rules": [
  {"id": "R1", "if": [["?p", "나이", "?a"]], "test": [["?a", ">=", {"n": "65", "unit": "세"}]],
   "then": ["?p", "할인율", {"n": "50", "unit": "%"}], "source": {"doc": "요금 규정 4조"}, "recorded": 6},
  {"id": "R2", "overrides": ["R1"], "if": [["?p", "섬주민", true]],
   "then": ["?p", "할인율", {"n": "100", "unit": "%"}], "source": {"doc": "요금 규정 4조 단서"}, "recorded": 7}],
 "changes": [
  {"recorded": 9, "retracts": "K02", "source": {"doc": "정정 공지"}}]}
```

각 항목의 뜻:

| 요구 | 표현 |
| --- | --- |
| 개체와 동일성 | `things[].id`. 진술은 식별자를 가리킨다. 이름은 찾기용이다. |
| 속성·관계 | `s`, `p`, `o`. `o`가 `{"thing": …}`이면 관계, 값이면 속성이다. 같은 형식이다. |
| 값 및 단위 | `{"n": "120", "unit": "명"}`. 수는 문자열 십진수로 적고 유리수로 계산한다. 그 밖에 `{"date"}`, `{"time"}`, `{"from","to"}`, `{"text"}`, `true`/`false`. |
| 규칙·전제 | `if`(변수 `?x`가 든 진술 무늬), `test`(비교), `then`(결론 진술. 값 자리에 계산식 가능). |
| 예외 | `overrides`. 일반 규칙을 누르는 규칙을 **명시적으로** 가리킨다. "더 구체적인 규칙이 이긴다" 같은 암묵 규칙은 두지 않는다. |
| 부정 | `holds: false`. 근거가 있는 거짓이다. 기록이 없는 것과 다르다. |
| 시간 | 적용 시간 `valid: [시작, 끝)`. 끝이 `null`이면 열려 있다. 기록 시간은 `recorded`다. 두 축의 뜻은 A.7에 고정한다. |
| 적용 조건 | `where`. "이 조건에서만 성립"을 뜻한다. 조건 하나짜리 규칙의 줄임 표기이며 같은 방식으로 평가한다. |
| 출처 | `source`. 모든 진술·규칙·변경에 필수다. 없으면 적재 때 "쓸 수 없음"으로 보고한다. |
| 변경 이력 | `recorded`(단조 증가 순번)와 `changes`. 기록은 지우지 않고 덧붙인다. 변경은 `supersedes`·`retracts`·`corrects` 세 가지다(A.7). |

**그래프 대응.** 진술 하나 = `relation` 노드 하나. `kind`=관계 리터럴, `subject`·`amount`=노드 참조(기존과 같음), 추가 리터럴 간선 `holds`·`from`·`to`·`where.*`·`source`. 개체 노드는 식별자당 하나다. 근거 span은 진술을 한 줄씩 정규 직렬화한 지식 본문의 위치를 가리킨다. 이렇게 하면 기존 `match.match`가 요구하는 "조건마다 본문 근거"(`match.py:152`)를 그대로 만족한다.

### A.3 질문 구조

질문도 같은 무늬다. `find`는 기존 스키마의 `project`와 같다.

```json
{"schema": "graph-question-v1",
 "find": ["?v"],
 "where": [["?ship", "정원", "?v"]],
 "names": {"?ship": "모래섬호"},
 "given": [],
 "at": "2026-12-01",
 "ask": "value"}
```

- `names`: 질문이 이름으로 가리킨 대상. 식별자 풀이는 실행기가 한다(애매하면 멈춘다).
- `given`: 질문이 가정한 전제. 예: "70세 승객" → `[["_p", "나이", {"n":"70","unit":"세"}]]`. 지식에 넣지 않고 그 질문에만 쓴다.
- `at`: 적용 시간 축의 기준 시점. 질문에 없으면 호출자가 준 `now`를 쓴다. 시스템 시계를 몰래 읽지 않는다(G12).
- `known_at`: 기록 시간 축의 기준 순번. 없으면 가장 최신이다. "그때까지 알던 것으로는 무엇이었나"를 물을 때만 준다(A.7).
- `ask`: `value`(값 찾기) · `check`(주장 확인. 기존 `claim` 관례의 일반화) · `count`/`sum`/`min`/`max`(답 집합의 집계).

### A.4 한 흐름으로 본 예 (설계 예제, 실행하지 않음)

사실 입력: 위 `R1`, `R2`와 아래 두 기록. (`K10`은 2026년 요금 5000원이다. A.7 참고.)

```json
{"id": "K11", "s": "t.fare", "p": "기본요금", "o": {"n": "6000", "unit": "원"}, "valid": ["2027-01-01", null], "supersedes": "K10", "source": {"doc": "요금표 2027"}, "recorded": 20},
{"id": "R3", "if": [["?p", "할인율", "?d"], ["t.fare", "기본요금", "?f"]],
 "then": ["?p", "낼요금", {"calc": ["*", "?f", ["-", {"n":"100","unit":"%"}, "?d"]]}], "source": {"doc": "요금 규정 5조"}, "recorded": 11}
```

질문: "섬 주민이 아닌 70세 승객이 2027년 2월 1일에 낼 요금은?"

```json
{"find": ["?x"], "where": [["_p", "낼요금", "?x"]],
 "given": [["_p", "나이", {"n":"70","unit":"세"}], {"s": "_p", "p": "섬주민", "holds": false}],
 "at": "2027-02-01", "ask": "value"}
```

적용 전제 및 연산 → 답 → 근거:

```json
{"status": "answered", "verification": {"steps": "agrees", "completeness": "agrees"}, "at": "2027-02-01", "known_at": 20,
 "answers": [{"value": {"n": "3000", "unit": "원"},
   "steps": [
    {"n": 1, "kind": "given", "fact": ["_p", "나이", "70세"]},
    {"n": 2, "kind": "rule", "id": "R1", "uses": [1], "test": "70세 >= 65세", "gives": ["_p", "할인율", "50%"]},
    {"n": 3, "kind": "given", "fact": ["_p", "섬주민", false]},
    {"n": 4, "kind": "exception_ruled_out", "rule": "R2", "over": "R1", "because": [3]},
    {"n": 5, "kind": "fact", "id": "K11", "valid": ["2027-01-01", null]},
    {"n": 6, "kind": "rule", "id": "R3", "uses": [2, 5], "calc": "6000원 × (100% − 50%) = 3000원", "gives": ["_p", "낼요금", "3000원"]}],
   "sources": ["요금 규정 4조", "요금 규정 4조 단서", "요금표 2027", "요금 규정 5조"]}],
 "assumptions": [], "reading": {"ignored": [], "loose_names": []}}
```

`given`에서 `섬주민` 줄을 빼면 4번 단계를 만들 수 없다. 그때 결과는 `needs_premise`이고 물을 것은 `["_p", "섬주민", ?]` 하나다.

### A.5 이 구조를 고른 이유

- 기존 그래프·팩·질문 형식과 같은 모양이라 reader·match·보고서가 그대로 이어진다.
- 조건·시간·부정·출처가 모두 "진술에 붙은 한정어"라서 기능마다 저장소를 나누지 않는다.
- 파생 결론을 저장하지 않으므로 수정 뒤에 낡은 결론이 남는 종류의 오류가 구조적으로 없다.
- 규칙의 무늬 문법(`?변수`, 세 항 무늬, `project`)은 기존 `QUERY-GRAPH-CONTRACT.md`의 것과 같다.

### A.6 이 구조가 표현하지 못하는 것

숨기지 않고 범위 밖으로 둔다. 범위 안이라고 주장하지 않는다.

- 결론이 "A 또는 B"인 규칙, 확률·정도("대체로", "거의").
- 명시적 `overrides` 없이 구체성으로 이기는 기본값 추론.
- 믿음·보고·의도 같은 중첩 문맥("ㄱ이 ㄴ이라고 말했다"의 ㄴ을 따로 추론). 출처는 진술의 한정어일 뿐 추론 대상이 아니다.
- "모든 X가 …" 같은 양화의 중첩. 집계(`count` 등)와 비교로 환원되는 것만 된다.
- 사건의 순서·지속에 관한 추론. 날짜 비교와 날짜+기간 계산만 된다.
- 선형이 아닌 단위 환산(섭씨·화씨), 방정식 풀이, 반올림 규칙(분야가 규칙으로 명시하지 않는 한 유리수 그대로 답한다).
- 지식에 없는 상식. "주말"이 토요일·일요일이라는 것도 분야 자료에 있어야 한다.

### A.7 두 시간 축과 세 가지 변경 (개정 1)

시간은 두 축이고 서로 섞지 않는다.

| 축 | 기록의 항목 | 질문의 항목 | 뜻 |
| --- | --- | --- | --- |
| 적용 시간 | `valid: [시작, 끝)` | `at` | 그 진술이 세계에서 성립하는 기간 |
| 기록 시간 | `recorded` (순번) | `known_at` | 지식 기반이 그 기록을 갖게 된 때 |

진술 하나가 질문에 쓰이는 조건은 둘 다다: `at`이 `valid` 안에 있고, 그 진술이 `known_at`까지 기록됐으며 `known_at`까지의 변경으로 철회되지 않았다.

변경은 세 가지이고 뜻이 다르다. 어느 것도 기록을 지우지 않는다.

| 변경 | 뜻 | 바꾸는 축 | 과거 날짜(`at`)를 물으면 |
| --- | --- | --- | --- |
| `supersedes` (날짜별 변경) | 세계가 바뀌었다. 새 진술의 `valid` 시작일에 이전 진술의 `valid` 끝을 닫는다. 이전 진술은 틀린 적이 없다 | 적용 시간 | 이전 진술이 그대로 답이다 |
| `retracts` (철회) | 그 기록은 처음부터 쓰면 안 됐다. 이 변경이 기록된 뒤로는 어떤 `at`에도 쓰이지 않는다 | 기록 시간 | 쓰이지 않는다. `known_at`을 변경 이전으로 주면 다시 보인다 |
| `corrects` (정정) | 내용이 틀렸다. 같은 순번에서 이전 진술을 철회하고 고친 진술을 넣는다 | 기록 시간 | 고친 진술로 답한다. `known_at`을 정정 이전으로 주면 틀렸던 내용이 보인다 |

예. 새 요금은 정정이 아니라 날짜별 변경이다.

```json
{"id": "K10", "s": "t.fare", "p": "기본요금", "o": {"n": "5000", "unit": "원"}, "valid": ["2026-01-01", null], "recorded": 10},
{"id": "K11", "s": "t.fare", "p": "기본요금", "o": {"n": "6000", "unit": "원"}, "valid": ["2027-01-01", null], "supersedes": "K10", "recorded": 20}
```

- `known_at` ≥ 20: K10의 적용 기간은 `[2026-01-01, 2027-01-01)`로 읽힌다. `at` 2026-12-01 → 5000원, `at` 2027-02-01 → 6000원. **K11이 들어온 뒤에 2026년을 물어도 5000원이다.**
- `known_at` = 15, `at` 2027-02-01: 5000원. 그때는 K11을 몰랐다. 답에 `known_at`이 표시된다.
- `supersedes`가 없는데 `single` 관계의 두 진술이 같은 `at`에 겹치면 충돌이다(B.2). 날짜 순서나 기록 순서로 한쪽을 이기게 하지 않는다.
- `supersedes`의 새 진술 시작일이 이전 진술의 시작일보다 앞이면 적재 때 쓸 수 없음이다. 그것은 정정으로 써야 한다.

**수정된 사실에 의존한 결론의 재검토(G8).** 변경이 기록되면, 과거 답의 영수증 가운데 영향받은 진술 식별자를 인용했고 그 답의 `at`이 바뀐 적용 기간 안에 있는 것을 돌려준다. `supersedes`는 새 시작일 이후의 `at`으로 낸 답만 영향받는다. `retracts`·`corrects`는 그 진술을 인용한 모든 답이 영향받는다.

## B. 실행 및 결과 계약

### B.1 지원 연산 (고정 제안 — 검토 뒤 확정)

| # | 연산 | 뜻 | 지금 상태 |
| --- | --- | --- | --- |
| O1 | 조회 | 무늬에 맞는 진술의 값을 **전부** 찾는다 | 있음 (`match.match`) |
| O2 | 연쇄 | 변수를 공유하는 여러 무늬의 결합 | 그래프 결합은 있음. 분야 관계 연쇄는 공개 검사 없음 |
| O3 | 규칙 적용 | `if`·`test`가 참이면 `then`을 얻는다. 얻은 것은 다시 전제가 된다 | 없음 |
| O4 | 예외 | `overrides` 규칙이 적용되면 눌린 규칙은 결론을 내지 않는다 | 없음 |
| O5 | 비교 | `=`, `≠`, `<`, `≤`, `>`, `≥`. 같은 차원의 수량, 날짜, 시각 | 주장 값의 문자열 일치만 있음 |
| O6 | 계산 | `+`, `−`, `×`, `÷`. 단위를 함께 계산하고 환산한다 | 없음 |
| O7 | 집계 | 답 집합의 `count`, `sum`, `min`, `max` | 없음 |
| O8 | 주장 확인 | 주장이 참·거짓·모름 중 무엇인지와 그 근거 | 조회 뒤 비교로 있음 (`_claim_query`) |
| O9 | 시점 선택 | `at`에 유효한 진술만 쓴다. 날짜+기간, 구간 포함 여부 | 없음 |

이 밖의 연산을 요구하는 질문은 `out_of_scope`다. 목록을 늘리려면 결과를 보기 전에 계약을 바꾼다.

### B.2 평가 순서

1. **적재 검사.** 형식, 출처 유무, 모르는 관계·단위, `overrides`의 순환, 같은 식별자의 중복을 검사한다. 어긴 기록은 버리지 않고 `unusable` 목록에 사유와 함께 남긴다(기존 `pack.load`의 `unusable`과 같은 방식). `overrides`가 순환하면 그 규칙 묶음 전체가 쓸 수 없음이다.
2. **유효 집합.** A.7의 두 조건으로 고른다: `known_at`까지 기록됐고 철회·정정되지 않았으며, `supersedes`를 반영한 `valid`가 `at`을 포함한다.
3. **대상 풀이.** 질문의 이름마다 개체 후보를 모은다. 하나면 통과, 여럿이면 `ambiguous_entity`, 없으면 그 이름은 모르는 대상이다.
4. **전제 추가.** `given`을 그 질문 한정 진술로 더한다.
5. **충돌 표시 (규칙 적용 앞).** 유효 집합과 `given`에서 충돌한 자리를 찾아 표시한다. 충돌한 자리란 (주어, 관계, 적용 조건)이 같고 (가) `single` 관계인데 값이 둘 이상이거나 (나) 같은 값에 `holds: true`와 `holds: false`가 함께 있는 것이다. 어느 쪽도 고르지 않는다. 출처의 날짜나 기록 순서로 몰래 이기게 하지 않는다. 이기게 하려면 A.7의 변경으로 명시한다.
6. **규칙 적용과 충돌 재검사.** 고정점까지 앞으로 적용한다. 한 규칙은 (가) `if`가 전부 **참**이고 `test`가 참이며 (나) 자신을 누르는 모든 규칙이 **적용되지 않음이 확인**될 때만 결론을 낸다.
   - 충돌한 자리는 참이 아니다. 따라서 어떤 `if`도 만족시키지 못하고, 예외가 적용되지 않는다는 근거로도 쓰이지 못한다. 그 자리에 막힌 규칙은 결론 대신 "충돌 때문에 막힘"을 충돌 자리와 함께 기록한다.
   - (나)에서 누르는 규칙의 조건이 모름이면 결론을 내지 않고 그 조건을 "부족 전제"로 기록한다. 충돌이면 "충돌 때문에 막힘"으로 기록한다.
   - 고정점에 닿으면 파생 결론을 포함해 5의 검사를 다시 한다. 새 충돌 자리가 나오면 그 자리를 표시하고 **파생 결론을 전부 버린 뒤 처음부터 다시 적용**한다. 표시는 늘기만 하므로 이 반복은 끝나고, 결과는 기록 순서나 규칙 적용 순서에 의존하지 않는다.
7. **질문 맞추기와 집계.** `where`를 만족하는 모든 묶음을 찾고 `ask`를 적용한다. 질문의 무늬가 충돌한 자리에 닿거나, 답에 필요한 파생이 "충돌 때문에 막힘"이면 결과는 `conflict`이고 충돌 자리의 양쪽과 막힌 경로를 낸다. 질문과 닿지 않는 충돌은 그 질문의 답을 막지 않는다.
8. **독립 확인.** 답과 단계 목록을 별도 확인 절차에 넘긴다(B.6).

**네 값 (개정 1).** 무늬 하나의 값은 넷 중 하나다.

| 값 | 조건 | 규칙의 `if`로서 | 예외를 배제하는 근거로서 |
| --- | --- | --- | --- |
| 참 | 맞는 진술만 있음 | 만족 | — (예외가 적용됨) |
| 거짓 | `holds: false` 진술만 있음, 또는 `absent_means: false` 관계에 아무 기록이 없음 | 불만족 | 쓸 수 있음 |
| 모름 | 아무 근거가 없음 | 불만족 | 쓸 수 없음 → `needs_premise` |
| 충돌 | 참의 근거와 거짓의 근거가 함께 있음, 또는 `single` 관계에 값이 둘 | 불만족 | 쓸 수 없음 → `conflict` |

빈 결과는 거짓이 아니다. 이는 기존 계약의 "no-evidence is not proof of logical negation"과 같은 원칙이다. 충돌은 모름과도 다르다. 모름은 물어서 풀 수 있지만 충돌은 지식을 고쳐야 풀린다. 그래서 묻지 않고 양쪽 근거를 보인다.

이 정의는 보수적이다. 한 번 충돌로 표시된 자리는 그 질문의 평가가 끝날 때까지 충돌이다. 충돌한 전제를 쓰지 않고도 같은 결론에 닿는 다른 경로가 있으면 그 결론은 정상적으로 나온다.

**순환과 한도.** 값이 새로 생기지 않는 순환(ㄱ→ㄴ→ㄱ)은 고정점에서 멈춘다. 계산으로 값이 끝없이 생기는 경우는 적용 횟수 한도에서 멈추고 `limit_exceeded`다. 한도는 팩 자료에 둔다(기존 `reading_recipe.json`의 관례 확장). 제안값: 연쇄 깊이 8, 규칙 적용 10,000회, 무늬 탐색 200,000걸음(기존 `match.match`의 `limit` 기본값), 질문당 10초. 한도에 닿으면 부분 결과로 답하지 않는다.

| --- | --- | --- | --- | --- |

| `conflict` | 근거가 서로 어긋남. 양쪽을 근거와 함께 낸다 | 충돌 | 없음 (동점 읽기의 hold만 있음) | `contradicted` |
| `limit_exceeded` | 탐색·적용·시간 한도에 닿음 | 한도 초과 | reader·match `hold` "search bound reached" | `incomplete_search` |

- 적재 실패나 예외는 상태가 아니라 오류로 따로 보고한다(기존 `error`).
- **상태 변경이 필요한 이유.** 지금은 `hold` 하나에 사유 문자열이 붙는다. 세금 시험의 Q22(읽지 못함)와 Q23(지식 없음)이 같은 `hold`였고 사람이 사유 문장을 읽어 구분했다. G9는 이 구분을 기계가 하도록 요구한다. 기존 필드(`reason`, `partial`, `executor`, `withheld`, `unknown_words`)는 없애지 않고 새 상태의 세부로 남긴다.
- **판정은 두 단계다 (개정 2).** 먼저 추론기가 **추론 상태**를 낸다. 그다음 확인 절차의 결과로 **최종 상태**를 정한다(B.6의 표). 결과에는 둘 다 남는다(`inferred`, `status`).
- **추론 상태의 순서.** 추론기 안에서 여러 조건이 겹치면 위에서 아래 순으로 하나만 낸다: 오류 → `not_understood` → `ambiguous_question` → `out_of_scope` → `ambiguous_entity` → `limit_exceeded` → `conflict` → `needs_premise` → `no_knowledge` → `answered`. 한도 초과가 지식 부재보다 앞인 이유: 탐색이 끝나지 않았으면 "없다"고 말할 수 없다. `verification_failed`와 `unverified`는 추론 상태가 아니다. 최종 판정에서만 생긴다.
- **`verification_failed`는 답 없는 결과에도 적용된다.** 추론기가 `no_knowledge`라고 했는데 확인 절차의 전수 열거가 답을 찾으면 그것도 거절이다. 이 상태는 지식이나 질문의 문제가 아니라 **구현 결함의 신호**이므로, 수용 판정에서는 실패이고 건수와 원인을 따로 보고한다.
- 기존 규칙 "실행기의 거부는 최종이다. 뒤의 예산 초과가 거부를 '검사 못 함'으로 바꾸지 못한다"(`CONTRACT.md`, `answer._second_opinion`)를 그대로 따른다.
- 주장 확인(O8)의 답은 `answered` 안에서 `claim: true | false`로 낸다. 모름이면 `no_knowledge`나 `needs_premise`다.

### B.4 세 경계

**자연어 입력과 구조 입력의 경계 = 질문 그래프(A.3)와 지식 기록(A.2).** 두 입구가 같은 구조를 만들고, 그 뒤는 한 길이다. 기존의 `answer.answer`(본문에서) / `answer.answer_graph`(그래프에서) / `pack.ask`가 이미 이 모양이다. 더할 것은 "질문도 구조로 받는 입구" 하나다. 구조 입구로 통과한 결과는 자연어 능력의 증거로 세지 않는다.

**언어 해석과 추론 검증의 경계.** 언어 쪽이 넘기는 것은 질문 그래프와 **읽기 영수증**이다. 영수증에는 질문의 모든 글자가 어느 조각으로 읽혔는지, 무시한 구절(`ignored`), 느슨하게 맞춘 이름(`loose_names`), 변형·알려 준 단어 사용이 들어 있다. 추론 쪽은 글을 다시 보지 않는다. 대신 영수증에 무시·느슨함이 하나라도 있으면 `answered`를 내지 않는다.

**정답 후보와 확정 답의 경계.** 확정(`answered`)은 다음이 모두 참일 때뿐이다: 질문 전체를 읽음, 이름이 정확히 또는 선언된 별칭으로 풀림, 탐색 완료, 충돌 없음, 전제 모두 근거 있음, 독립 확인의 단계 대조와 완전성 대조가 모두 일치. 읽기가 불완전하거나 확인을 하지 못했으면 `unverified`이고 어느 것이 빠졌는지 적는다. 확인 절차가 거절했으면 `verification_failed`다. 세금 시험의 Q16·Q20·Q24(값은 맞았으나 구절을 무시)는 이 계약에서 `unverified`다. **수용 판정에서 `unverified`는 성공이 아니다.**

현재 이름 대조의 3단계 "앞말 무시"(`match.name_fit` level 2)는 수식어를 버리는 규칙이다. G2·G3와 맞지 않으므로 확정 답의 길에서는 뺀다. 앞말은 조건(`where`·`given`)으로 읽히거나, 읽히지 않으면 답을 확정하지 않는다.

### B.5 단위·시간·출처를 답까지 잃지 않는 방법

- 답의 값은 문자열이 아니라 값 객체다(`{"n", "unit"}`). 문장으로 쓰는 것은 마지막 단계의 일이고, 쓴 문장을 다시 읽어 같은 값 객체가 나와야 한다(기존 `write.say`의 되읽기 규칙을 값까지 넓힘).
- 답마다 `steps`가 붙고, 단계는 진술·규칙 식별자를 가리키며, 식별자는 출처를 가진다. 근거 없는 단계가 하나라도 있으면 답하지 않는다(기존 `match.py:152`의 원칙).
- 답에 쓴 `at`과 각 진술의 `valid`를 함께 낸다. 가정(`absent_means: false` 사용)은 `assumptions`에 낸다.
- 조건부로만 성립하는 답은 조건과 함께 낸다. 조건을 떼고 값만 내는 출력 형식은 두지 않는다.

### B.6 독립 확인 절차

확인 절차는 (지식, 질문 그래프, 결과)만 받는다. 추론기의 코드를 불러 쓰지 않는다. 대조는 둘이고 **둘 다 일치해야** `answered`다(개정 1).

**(1) 단계 대조 — 낸 답이 옳은가.** 탐색하지 않고 단계를 하나씩 본다: 인용한 진술이 있고 `at`·`known_at`에 유효한가, 충돌로 표시될 자리를 인용하지 않았는가, 규칙의 대입이 인용한 단계들과 맞는가, `test`와 `calc`를 다시 계산해 같은가, 눌린 예외마다 "적용되지 않음"의 근거 단계가 있는가.

**(2) 완전성 대조 — 빠진 답이 없는가.** 단계 대조는 근거가 맞는 답 하나만 낸 결과도 통과시킨다. 그래서 확인 절차가 답 집합을 **스스로 다시 구해** 결과의 답 집합과 같은지 비교한다. 방법은 추론기와 다른 알고리즘이다: 색인도 되추적도 없이, 유효 집합을 무늬 수만큼 겹쳐 돌며 조건을 거르는 전수 열거다. 규칙이 있는 단계에서는 색인 없는 단순 반복 적용으로 닫힘을 따로 구한다. 답 없는 결과(`no_knowledge`, `ambiguous_entity`, `conflict`, `needs_premise`)도 같은 열거로 대조한다.

최종 판정표 (개정 2). 위에서부터 처음 맞는 줄을 쓴다.

| 추론 상태 | 확인 결과 | 최종 상태 |
| --- | --- | --- |
| `limit_exceeded` | 확인하지 않음 | `limit_exceeded` |
| **무엇이든** (`no_knowledge`, `ambiguous_entity`, `conflict`, `out_of_scope` 포함) | 단계 대조나 완전성 대조 중 하나라도 거절 | `verification_failed` — 원인: 어느 단계인지, 빠지거나 남는 답, 또는 "추론 상태는 X인데 확인은 Y" |
| 무엇이든 | 거절은 없고 하나라도 한도로 못 함 | `unverified` — 추론 상태를 `inferred`에 남긴다 |
| `answered` | 둘 다 일치 | `answered` |
| `no_knowledge`, `ambiguous_entity`, `conflict`, `out_of_scope`, `needs_premise` | 둘 다 일치 | **추론 상태 그대로.** 일치는 답 없는 결과를 `answered`로 바꾸지 않는다 |

거절이 "못 함"보다 앞이다. 단계 대조는 거절했고 완전성 대조는 한도로 못 한 경우 거절이 남는다. `not_understood`와 `ambiguous_question`은 언어 쪽 상태라 이 절차의 대상이 아니다(F.3).

전수 열거의 한도(제안: 겹쳐 도는 조합 수 1,000,000)도 팩 자료에 둔다. F.2의 크기 한도에서 무늬 셋 이상의 질문은 이 한도에 걸릴 수 있다. 그 비율이 얼마인지는 구현 뒤에 재야 안다. 걸린 질문은 `unverified`이고 통과가 아니므로, 한도에 자주 걸리면 열거 방법을 바꿔야 한다(F.6).

**이 절차가 보지 못하는 것.** 질문 그래프가 질문의 뜻과 같은지는 전혀 보지 않는다(F.3). 완전성 대조는 같은 사람이 같은 계약을 읽고 쓴 두 번째 구현이므로, 계약 자체를 잘못 이해했으면 둘이 같이 틀린다.

기존 두 번째 의견(`answer._second_opinion` → `native.run_pair`)은 조회에 한해 유지할 수 있으나, 인계 문서에 따르면 두 문장 정도를 넘으면 탐색 예산이 떨어진다. 세금 시험 156회에서 `verified=true`는 0개였다. 따라서 이것을 주 확인 수단으로 삼지 않는다.

4. **전수 열거의 한도 초과율을 재지 않았다.** 여객선 팩은 진술 7개다. 목표 규모(진술 500개)에서의 값은 모른다.
5. **두 구현은 같은 작성자가 썼다.** 일치는 내부 교차검사다. 개발 중 두 구현이 어긋난 적은 없었는데, 그것은 둘이 같은 오해를 공유한다는 뜻일 수도 있다.
6. **추론 상태의 순서가 B.3과 조금 다르다.** 이름을 차례로 풀다가 모르는 이름을 만나면, 뒤의 이름이 애매하더라도 `no_knowledge`를 먼저 낸다.
7. 근거는 진술 식별자다. A.2의 "정규 직렬화 본문 위치"와 기존 그래프 형식으로의 변환은 만들지 않았다(6단계).
8. 날짜·시각 값은 같은지만 비교한다. 수는 `Fraction`으로 다루고 답에는 `"7/2"` 꼴로 나올 수 있다.
9. 주장 확인은 무늬 하나, 주어와 값이 정해진 것만 받는다. 그 밖은 `out_of_scope`다.

## F. 평가 설계와 미결정 사항

### F.1 세 평가의 분리

| 평가 | 고정하는 것 | 바꾸는 것 | 입력 | 재는 것 |
| --- | --- | --- | --- | --- |
| S 구조화된 지식 처리 | 코드 | 분야 | 지식도 질문도 구조(A.2, A.3) | 추론·상태·근거의 정확성. 자연어 능력의 증거가 아니다 |
| L 표현 일반화 | 코드, 언어 팩, 분야 지식 | 질문의 표현 | 개발에 공개된 분야에 대해 독립 출제자가 쓴 새 문장 | 문장을 질문 그래프로 옮기는 능력. 출제자가 쓴 질문 그래프와 비교 |
| T 분야 이전 | 코드, 언어 팩 (해시로 고정) | 분야 전체(어휘·사실·규칙) | 새 분야의 팩 + 자연어 질문 | G11. 고정 뒤 분야 팩 외의 변경이 있으면 무효 |

세 평가의 점수는 합치지 않는다. T가 최종 수용에 가장 가깝고, S와 L은 실패가 추론 쪽인지 언어 쪽인지 가르는 데 쓴다.

### F.2 독립 평가 구성 (제안 — 수량은 검토에서 확정)

- **분야.** 최종 시험 분야 3개. 독립 출제자가 정하고 구현 담당은 모른다. 세금·도서관·여객선은 개발에 노출됐으므로 제외한다.
- **한 분야의 문항 칸.** 답할 수 있는 질문: 연산 O1~O9 × 4 = 36. 답할 수 없는 질문: 7종(이해 실패, 범위 밖, 애매한 질문, 애매한 대상, 지식 부재, 전제 부족, 충돌) × 3 = 21, 한도 초과 2. 수식어 대조 쌍 8쌍 = 16. 합 75문항. 3분야 225문항.
- **분모 공개.** 칸마다 통과·오답·부당 보류·상태 오분류를 따로 센다. 평균으로 합치지 않는다. 통과 조건은 수용 기준 6절대로 오답 0, 부당 보류 0, 그리고 `unverified`와 `verification_failed`는 통과가 아니다. `verification_failed` 건수는 따로 보고한다.
- **지식 크기 한도.** 분야당 개체 200, 진술 500, 규칙 50 이하. 연쇄 깊이 8 이하.
- **자원 한도.** 질문당 10초(세금 시험의 본문 경로와 같음), 프로세스 하나, 메모리 512MB, 재시도 없음, 첫 응답만 기록.
- **절차.** 코드·언어 팩·설정의 해시를 먼저 고정해 제출한다. 출제자는 수업·실패 문항을 보지 않는다. 문항과 정답은 구현 담당에게 주지 않는다. 한 번 실행한다. 공개된 문항은 회귀 검사가 되고 재판정은 새 시험으로 한다.
- 구현 담당은 최종 문항과 정답을 쓰지도 요구하지도 않는다. 출제자에게 줄 것은 A.2·A.3 형식 설명서와 B.1·B.3 계약, 그리고 자연어 범위 설명서뿐이다.

### F.3 별도 검증기가 같은 결함을 공유할 위험

- **같은 질문 그래프를 받는다.** 기존 두 번째 의견과 B.6의 확인 절차는 모두 reader가 만든 질문 그래프에서 출발한다. reader가 수식어를 버리고 읽으면 두 방법이 같은 틀린 질문에 같은 답을 내고 "일치"한다. 세금 Q24가 그런 꼴이었다(구절을 무시했는데 값은 맞음).
- **되읽기는 같은 reader다.** `write.say`가 쓴 문장을 같은 reader가 읽는다. reader가 두 뜻을 구분하지 못하면 되읽기도 통과한다. 수용 기준이 이미 밝혔듯 이것은 내부 일관성 검사다.
- **같은 팩을 읽는다.** 적재 단계가 값을 잘못 해석하면 추론기와 확인 절차가 같은 틀린 지식을 본다.
- **같은 저자다.** 구현 담당이 쓴 확인 절차는 같은 오해를 품을 수 있다.

줄이는 방법(없애지는 못한다):

1. 언어 쪽은 평가 L에서 **출제자가 쓴 질문 그래프**와 비교한다. 답 값 일치로 대신하지 않는다.
2. 읽기 영수증으로 질문의 모든 글자가 조각에 덮였는지 기계로 검사한다. 덮이지 않은 글자가 있으면 확정 금지.
3. 대조 쌍(D15 꼴). 수식어 하나만 다른 두 질문의 답이 달라야 통과.
4. 확인 절차는 추론기 코드를 불러 쓰지 않고 팩 원본을 따로 읽는다. 가능하면 다른 사람이 쓴다.
5. 구조 평가 S의 정답은 출제자가 손으로 푼 것이다. 어떤 구현의 출력도 정답 작성에 쓰지 않는다.

### F.4 자연어 범위에 관한 제안 (원래 목표와의 차이 명시)

원래 목표는 "지식을 넣으면 그 지식에 관해 완벽하게 답한다"이고 자연어 범위에 제한을 두지 않았다. 수용 기준 2절은 범위를 먼저 명시하라고 했다. 아래는 그 **제안**이다. 완료 기준을 바꾸는 것이 아니며 검토에서 넓히거나 좁힐 수 있다.

- 제안: 범위를 표현이 아니라 **뜻의 틀**로 정한다. (1) 속성 진술·질문 (2) 두 대상의 관계 (3) "~이면 ~이다" 규칙 (4) "다만 ~이면" 예외 (5) 부정 (6) 시점·기간 한정 (7) 수량과 단위 (8) 주장 확인 (9) 가정 전제가 든 질문 (10) 집계. 틀마다 조사 변형과 어순 변형은 범위 안이다.
- 원래 목표와의 차이: 대명사·생략의 복원, 문장을 넘는 지시, 함의, 자유로운 문단 형태의 지식 입력은 범위 밖이 된다. 틀에 맞지 않는 문장은 `not_understood`가 옳은 결과가 된다. 이것은 "어떤 문장이든"보다 좁다.
- 근거: 현재 reader가 읽는 틀은 2개이고 가르치지 않은 표현은 보류된다(인계 문서 7절). 세금 시험의 자유로운 질문 10개(Q15~Q24) 중 무시 표시 없이 값이 맞은 것은 1개였다(같은 보고서).
- 수업만 늘려 틀 10개를 읽게 할 수 있는지는 **모른다**. reader의 조각·역할 모형이 절 둘("~이면 ~이다")을 한 그래프로 잇지 못할 가능성이 있다. 6단계 첫머리에 공개 예제로 먼저 확인하고, 코드 변경이 필요하면 그 필요를 보인 뒤 제안한다.
- 자연어 지식 입력(8단계)을 최종 수용에 넣을지 뺄지도 결정이 필요하다. 빼면 G1은 구조 입력으로만 충족되고, 이는 원래 목표의 "지식을 넣으면"보다 좁다.

### F.6 이 설계의 알려진 약점

- 규칙을 질문마다 처음부터 다시 적용한다. 지식이 F.2의 크기 한도를 크게 넘으면 느려진다. 그때는 결론에 의존 식별자를 붙여 저장하는 방식으로 바꿔야 하고, 그 순간 수정 반영이 다시 문제가 된다.
- 답의 완전성은 전수 열거로 대조한다(B.6). 열거는 무늬 수에 지수적이라 큰 지식·긴 질문에서 한도에 걸리고, 걸리면 `unverified`라 통과가 아니다. 얼마나 자주 걸리는지는 재 보지 않았다.
- 충돌 처리가 보수적이다(B.2). 파생 결론끼리 충돌하면 전부 버리고 다시 적용하므로 충돌이 많은 지식에서는 느리다. 또 `single` 선언을 잘못 붙이면 정상인 복수 값이 충돌이 된다.
- 기록 시간은 순번이지 날짜가 아니다. "작년 11월에 알던 것"처럼 날짜로 묻는 것은 순번과 날짜의 대응표가 따로 있어야 한다. 이번 범위에 넣지 않았다.
- `overrides`를 사람이 빠뜨리면 두 규칙이 둘 다 적용돼 `conflict`가 난다. 틀린 답보다는 낫지만 부당 보류로 셀 수 있다. 이것은 지식 작성의 책임으로 본다.
- 추론 코드는 Python이다. "최소 Python, 최대 그래프"에 비추면, 분야 동작은 전부 팩 자료지만 평가 절차 자체는 그래프 프로그램이 아니다. 기존 실험도 같은 상태다(인계 문서 7절).
- 이 문서의 어떤 주장도 실행으로 확인되지 않았다.
