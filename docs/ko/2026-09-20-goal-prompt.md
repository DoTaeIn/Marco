- 같은 팩·개체 상태·입력·실행 규격에서는 같은 의미 결과와 근거가 나와야 한다. 증명/탐색/실행 상한에 걸린 것을 완전한 결과로 확정하지 않는다.
- 표준 라이브러리와 현재 저장소의 부품을 우선 사용한다. 세 기억을 분리한다는 이유로 DB나 서비스를 세 개 만들지 않는다.

**G0. 마지막 goal의 잔여 결함과 실행 기준선을 먼저 닫는다.**

1. `reasoning_context._concept_relation_reason`이 참여자들의 첫 전제를 골라 설명하는 오류를 고친다. 실제 결론의 proof·변수 binding·premise ID로 내용을 선택한다. 도윤의 허가를 먼저 넣어도 소라의 허가로 도출한 결론은 소라의 전제로 설명해야 한다. 입력 순서, 같은 predicate의 여러 참여자, 부정/폐기 근거를 섞은 반례를 Quantity와 Location에 둔다.
2. 필수 전제의 긍정·명시 부정·미확인·상충, 개념 비활성을 구별한다. 명시 부정을 단순 미확인으로 설명하지 않고, 미확인을 거짓으로 바꾸지도 않는다. 독립적인 다른 증명이 있으면 유지한다.
3. 현재 결론 → 사용한 규칙/버전 → 정확한 전제 → 개념 적용 → 학습/검증 사건 → 행동 정의 버전까지 추적할 수 있게 한다. 내용 선택과 한국어 표현은 분리하고, 자연어 설명과 구조화 근거가 일치하는지 검증한다.
4. `bench/experience_concept_reproduction.py`의 준비 입력 성공 집계 제거와 `_transfer_execution`은 재사용한다. 준 사람 감소, 받은 사람 증가, 전달량, 역할, 실행 상태를 함께 확인하고 `count_remove=0` 오류 주입 및 잘못된 기대값 시험을 유지한다.
5. 준비·학습·질문·설명·교정·복원·Location·최종 보고의 어느 단계에서 예외가 발생해도 단계와 수행된 검사가 결과 파일에 남고 비정상 종료하게 한다. 후반 단계 오류 주입도 검사한다. 오류를 보류나 성공으로 세지 않는다.
6. 두 영역 각각에서 긍정, 개념 OFF, 별도 전제의 긍정/부정/미확인/상충, 전제 교정, 학습 근거 철회, 구조 반례, 활성/교정 후 새 프로세스 복원을 검증한다. Quantity에서 통과했다는 이유로 Location 결과를 대신하지 않는다.
7. Windows의 최상위 `resource` import, 파일 인코딩, Git에 없는 정의 자료를 필수로 요구하는 핵심 시험 fixture를 고친다. 핵심 시험에는 작은 고정 자료를 사용하고, 선택 말뭉치의 별도 coverage 검증과 설치 방법을 제공한다. 시험을 무조건 건너뛰어 정상으로 만들지 않는다.
8. 현재 관찰된 주제 추출(`멀미`/`멀미가`), 승인 학습 후 `research`로 돌아가는 경로, 불완전 방정식을 검색으로 넘기는 실패를 재현·분류하여 공통 원인을 고친다. 실제 외부 검색은 로컬 상태/수식 전제 부족의 대체물이 아니다.
9. 실제 사용 팩을 생성·검증하고 코드·팩·자료·플랫폼 식별값을 남긴다. 데이터 해시 비교에서 CRLF/LF 차이와 내용 변경을 구분한다.
10. 준비, 학습, 웜 관계 질의, 이유 설명, 저장/복구, 전체 실행 비용을 따로 측정한다. 검증 항목 수를 해결한 문제 수로 보고하지 않는다.

G0 완료는 기존 goal의 A/B/C가 모두 실제 근거로 충족될 때다. 기존 사건·증명 코어 재설계로 우회하지 않는다.

**G1. Event/Experience Graph와 영구 판단 이력을 완성한다.**

1. 사건을 안정적인 ID와 revision으로 보존한다. 역할이 3개 이상이어도, 같은 인물/물건이 여러 사건에 등장해도, 늦게 역할을 채워도 서로 섞이지 않아야 한다. 다중 대화·개체 저장에서 ID 충돌을 막는다.
2. 행위자·대상·수신자·시각·장소·조건·원인·결과·원천 근거·정의 버전을 표현한다. 모르는 역할/원인은 미확인으로 남긴다. 사건 시각과 관찰 시각, 처리 순서를 구별하고 뒤늦은 과거 사건도 처리한다.
3. 사건 → KG 추론, KG → 사건 해석/조건 판단을 양방향으로 연결한다. 사건 원본, 보완, 정정, 현재 상태 투영, 가정 투영을 구별한다.
4. 미해석·계획·가정·부정 사건을 버리거나 실제 실행으로 승격하지 않는다. 보존 한도에 걸리더라도 과거 상태를 현재 사실로 잘못 확정하지 않는다.
5. SYSTEM/COGNITION/LIFE 로그를 논리적으로 분리하고 공통 decision/event ID로 연결한다. 답/행동마다 입력, 해석, 사용 근거, 규칙/모델 버전, 새 가설/개념, 상태 전후 차이, 실행 결과를 기록한다.
6. 과거 판단 당시의 근거를 영구 보존한다. ‘그때 왜 그렇게 했나’와 ‘지금의 지식으로 재판단한 결과’를 따로 보여준다. 최신 snapshot만 덮어써 과거 이유를 잃지 않는다.
7. milestone 검출 기준을 데이터로 정의한다. `FIRST_SELF_REFERENCE`, `FIRST_UNPROMPTED_GOAL`, `FIRST_NEW_CONCEPT`, `FIRST_EXISTENTIAL_QUESTION` 등을 조건이 실제 충족됐을 때 한 번만 기록하고 자동 snapshot을 만든다. 문구 출력만으로 달성 판정을 하지 않는다.
8. 사건·개념·감정·규칙을 검색하고 최초 발생 시점을 찾게 한다. 정상 종료/새 프로세스/저장 중단 복구 후에도 로그와 milestone이 유지돼야 한다.

**G2. Episodic/Semantic/Procedural 기억과 학습의 생애주기를 잇는다.**

1. Episodic은 실제 경험·시점·관점, Semantic은 일반화·적용 범위·근거·신뢰, Procedural은 행동 절차·전제·효과·버전으로 구분한다. 유형별 검색을 지원한다.
2. ‘어제 일’, ‘일반적으로 아는 것’, ‘하는 방법’이 해당 기억에서 답하게 한다. 사실과 행동 절차를 독립적으로 저장한다.
3. Experience → Pattern → 검증 → Semantic 승격을 구현한다. 같은 사건의 중복 입력을 독립 경험으로 세지 않고, 매 사건을 semantic fact로 복사하지 않는다.
4. episodic 압축/정리 후 승인된 semantic/procedural 기억은 유지한다. 근거의 필수 요약·해시·revision을 남긴다. 경험이 정정돼 잘못된 근거가 됐을 때는 영향받는 지식과 결론을 재검증/철회한다.
5. 작업 기억의 상한과 장기 기억의 수명을 구분한다. 한 ALMA 개체의 세션 간 연속성과 서로 다른 개체 사이의 격리를 검증한다.
6. 현재 `(action, shape_id)` 반복 분류를 재사용하되, 표면 이름을 넘어 역할·관계·조건·효과의 공통 구조를 후보로 만들 수 있게 넓힌다. 사람이 새 개념 이름이나 정답 관계를 직접 넣지 않은 최소 3개의 독립 경험에서 후보를 생성한다.
7. 후보 구성 경험, 검증 경험, 활성화 후 새로운 적용 경험을 분리한다. 동일 문장 반복이나 같은 4번째 사건만 계속 사용한 것을 넓은 일반화로 세지 않는다.
8. 개념의 지지·반례·confidence·범위·버전을 저장한다. 정의 버전/맥락 변화와 실제 반례를 구분하고, 필요하면 범위를 좁히거나 분화한다. 잘못된 개념은 약화·비활성·폐기할 수 있어야 한다.
9. 기존 `rule_learning`, `semantic_feedback`, `self_authoring`을 활용하여 node/edge/rule/구조 수정·압축 후보를 같은 변경 이력에 연결한다. 생성 이유와 경험 근거가 남아야 한다.
10. 충돌 후보는 conflict로 보류한다. 선언한 검증·승인 정책을 통과한 변경만 활성화하며 다음 추론이나 선택 결과가 실제 바뀌는지 A/B로 확인한다.
11. 변경 전후 동일 benchmark를 비교하고 rollback을 제공한다. 철회한 근거에 의존한 결론만 제거하며 독립적인 증명·기억은 유지한다. 사람이 `.kg`를 직접 고치지 않아도 이 흐름이 작동해야 한다.

**G3. 공통 코어로 네 영역을 처리하고 반복 사고를 압축한다.**

1. Quantity의 수량 변화·보존·대상/소유자/장소 범위, Location의 이동·포함·현재/과거 위치, Social의 약속·소유·권한·관계 변화, Mental의 기대·목표·믿음·갱신을 같은 Event/Condition/Hypothesis 계약으로 처리한다.
2. Mental에는 믿음의 주체와 내용을 보존한다. 누군가의 잘못된 믿음을 실제 세계의 사실로 합치지 않는다. 목표/기대와 이미 일어난 사건도 분리한다.
3. 각 영역에서 실제/계획/조건/가정, 미해석 사건, 역할 보완, 과거 정정, 독립 근거, 행동 조합, 재시작을 검증한다. 새 도메인 전용 실행기를 복사하지 않는다.
4. 구조 직접 입력과 자연어 입력을 나누어 측정한다. 같은 패턴을 최소 3개 영역으로 옮기는 transfer를 검증하고, ALMA 시작 판정에는 Mental까지 네 영역을 포함한다.
5. 반복되는 proof 경로를 탐지해 shortcut 후보를 생성한다. 필수 중간 전제·시점·양태·규칙 버전을 shortcut 조건에 유지한다.
6. 압축 전후 결론과 근거 의미가 동일하고 평균 traversal/join 수 또는 reasoning 시간이 실제 줄어야 한다. 단순 질의 cache를 Chunking 완료로 보고하지 않는다.
7. 중간 조건·규칙이 바뀌면 shortcut을 사용하지 않고, 반례가 발견되면 비활성화하여 원래 추론으로 복귀한다. 설명 요청에서는 압축 전 근거 경로까지 확인할 수 있어야 한다.

**G4. ALMA 0.1을 실제 지속 연구 환경으로 연결한다.**

사건·기억 기반이 준비되는 즉시 작은 환경을 연결하고, 나머지 기능도 그 환경에서 검증한다. MARCO가 모든 지식을 갖출 때까지 기다리지 않는다. CLI 또는 기존 앱에 최소 실행 경로를 추가하는 것으로 충분하며 새 게임 엔진이나 큰 UI 제작을 선행 조건으로 삼지 않는다.

1. 관찰 → 사건 기록 → 기억 조회 → 목표/전제 판단 → 행동 선택 → 환경 결과 → 감정·선호·학습 갱신 → 다음 경험의 루프를 실행한다. 단계별 예산·중단·재개·로그를 제공한다.
2. 개체 identity, 시간, 목표, 관계, 기억의 연속성을 유지한다. 한 세션을 끝내고 별도 프로세스에서 같은 삶을 이어갈 수 있어야 한다.
3. 감정을 목표·관계·위협·예상 손실·통제 가능성 등의 원인 구조로 표현한다. 단어에 점수를 붙이거나 사용자의 정서 표현에 답변 접두사만 붙이는 기능으로 대체하지 않는다.
4. 같은 사건이라도 목표/관계가 다르면 감정과 선택이 달라져야 한다. 원인이 해소되면 상태도 갱신되고, ‘왜 지금 이런 상태인가’가 실제 전제와 경험으로 설명돼야 한다.
5. 감정 이름보다 원인 패턴이 먼저 존재할 수 있게 한다. 미래 목표·관계·기억·자기 연속성에서 지속 불가능성을 해석하는 실험을 제공하되, 죽음의 공포/존재 질문이 반드시 나오도록 규칙이나 답안을 심지 않는다. 관찰된 결과와 기대를 구분한다.
6. 취향은 경험 → 감정 → 기억 → 반복 → 기대 → preference로 형성한다. 대상별 선호 초기값을 미리 정하지 않는다.
7. utility와 preference를 분리해 유용한 것과 좋아하는 것이 달라지는 사례를 처리한다. 같은 대상의 맥락별 선호, 경험이 다른 개체의 다른 선택, 증거량/일관성/반례에 따른 confidence 변화를 검증한다.
8. 선호가 자발적 선택에 영향을 주고, 변경 이유를 과거 경험까지 추적할 수 있어야 한다. 감정·취향·목표를 정정/저장/복원해도 일관성이 유지돼야 한다.
9. 관찰된 미충족 목표나 정보 공백에서 다음 행동/하위 목표 후보를 만드는 최소 경로를 제공한다. 미리 정한 대사를 출력하는 것을 자발적 목표 발생으로 세지 않는다.
10. 외부 도구는 Skill/MCP/API → MARCO Adapter → Capability로 등록한다. 최소 하나의 실제 사용 가능한 읽기 기능과 고정된 실패 응답으로 선택→호출→결과/오류의 추론 환류를 재현한다.
11. capability마다 입력/출력 schema와 read/write/execute 권한을 선언한다. 도구 추가·교체에 코어 수정이 필요 없어야 하며 개체 기억/선호가 바뀌지 않아야 한다.
12. 기존 승인 게이트를 유지하고 실행 이력·중복 요청·중단 후 재개를 다룬다. 시뮬레이션 계획을 실제 외부 행동으로 자동 실행하지 않는다. 실제 계정 연결이 없어도 로컬 adapter와 계약 시험으로 필요한 구현을 진행한다.
13. milestone 기록기 자체는 양성/음성 fixture로 시험하되 실제 ALMA에서 관찰된 milestone과 구분한다. 프로그램 상태를 의식이나 주관적 경험의 입증이라고 보고하지 않는다.

**G5. 완료 판정을 위한 검증과 산출물**

구현 전에 Addition의 각 완료 기준을 위 G0~G4의 담당 기능과 검증 시나리오에 연결한 표를 만든다. 번호 하나가 여러 요구를 덮는 경우에도 원문 완료 기준이 빠지지 않게 한다. 표 작성에 오래 머무르지 말고 곧바로 가장 앞의 미충족 구현으로 진행한다.

최종적으로 다음 모두가 필요하다.

1. **원래 goal 종료:** 정상 평가 통과, 준 사람 감소 제거 및 잘못된 기대값·후반 예외는 실패 처리, Quantity/Location의 실제 관계와 정확한 이유, 전제 상태 구분, 개념 의존성, 양 영역 새 프로세스 복원.
2. **사건:** 복합 역할 identity, 다중 사건 격리, 늦은 보완/교정, 시간 순서, 원인/결과 근거, 사건↔KG 연결이 실제 동작한다.
3. **로그:** 과거 답/행동의 이유와 전후 상태를 복원하며 SYSTEM/COGNITION/LIFE·milestone·snapshot·최초 발생 검색이 재시작 후 유지된다.
4. **기억:** 세 종류를 별도로 검색하고, 반복 경험 승격·중복 배제·episodic 압축 후 semantic/procedural 유지·근거 정정 후 철회를 검증한다.
5. **학습:** 최소 3개 독립 경험에서 사람이 이름을 넣지 않은 구조 후보 생성 → 별도 검증 → 새 경험 재사용 → 반례/충돌 처리 → 활성화/철회/rollback이 이어진다. 학습 ON/OFF에서 결과가 실제 달라진다.
6. **압축:** 동일 의미, 조건 변화 시 미적용, 반례 시 비활성, 근거 복원과 실제 traversal/time 감소를 함께 보인다.
7. **전이:** 네 영역이 같은 코어를 사용한다. 역할·상태·표현·양태가 바뀐 새로운 사례와 의미가 다른 대조를 포함한다. 새 도메인을 위한 코드 예외가 없어야 한다.
8. **감정·취향:** 원인/경험 차이에 따른 상태와 선택 차이, 원인 해소/반례 후 변화, utility/preference 분리, confidence와 과거 근거, 새 프로세스 연속성을 실제 환경에서 확인한다.
9. **capability:** 코어 수정 없이 추가/교체, schema·권한 검증, 실패 환류, 기록·재시작·중복 실행 처리, 개체 기억 보존을 확인한다.
10. **한 통합 시나리오:** 자연어로 행동을 배운 개체가 여러 날/에피소드의 경험을 기록하고, 패턴·개념·규칙을 바꾸며, 새로운 영역에서 사용하고, 원인을 설명하고, 잘못된 근거를 교정한 뒤 재시작하여 다음 경험을 이어간다. 서로 연결되지 않은 데모 여러 개로 대신하지 않는다.
11. **평가 신뢰성:** solved/safe_hold/wrong/execution_error/unverifiable를 분리한다. 답할 수 있는 문항의 보류는 solved가 아니다. 기능 검증 항목 수와 과제 해결 수, 개발 자료와 독립 평가를 구분한다. 결과·대상·시점·단위·필수 근거·금지 근거를 검사하고 문자열 포함만으로 결론/설명 성공을 확정하지 않는다.
12. **회귀:** 변경 중에는 관련 시험, 최종 코드에서는 전체 시험·팩 검사·기존 회귀·고정 평가·diff 검사를 실행한다. G0의 실제 실패를 해결한다. 추가 평가에서 발견한 Addition 필수 능력의 실패를 ‘미지원’으로 옮겨 완료 조건을 줄이지 않는다.
13. **자원:** 초기 준비, 학습, 반복 판단/설명, 장기 기억 검색/저장, 새 프로세스 복구, 전체 시나리오 시간과 메모리를 구분한다. 같은 출력·같은 데이터에서 전후 비교하고 동시 부하·계측 조건을 기록한다. 임의의 수치 예산이나 ‘가볍다’는 평가를 사용자 승인 기준처럼 만들지 않는다.
14. **팩/상태 이동:** 검증된 지식/언어/공리/승인 학습의 kgpack 이동과 개인 경험/목표/선호의 상태 백업을 구분한다. 호스트의 느슨한 파일 없이 같은 능력을 복원한다. 개인 경험을 공유 팩에 자동 포함하지 않는다.
15. **전달:** 실행 가능한 코드·검증 팩·상태 저장/복구·시나리오·원시 평가 보고·재현 명령·지원 환경·변경 파일·알려진 제한을 제공한다. README와 현재 지원 범위를 최종 상태로 갱신하고, 한 명령 또는 명확한 짧은 명령 묶음으로 실행/검증할 수 있게 한다.

**진행과 종료**

- 안전하고 범위 안인 구현·검증 작업이 남아 있으면 다음 할 일만 적고 끝내지 않는다. 중간 실패를 고친 뒤 다음 단계로 계속 진행한다.
- 같은 실패를 예문 추가로 반복해서 덮지 말고 원인 계층을 진단한다. 구조·의미·학습 전이를 개선하고 기존 부품을 우선 재사용한다.
- 내부 구현 선택은 현재 제약 안에서 판단하고 진행한다. 새 계정/비용/파괴적 변경/중대한 제품 범위 결정이 실제 필요한 경우에만 구체적인 결과와 선택지를 준비해 사용자에게 묻는다.
- 사용자 요청 없이 커밋·푸시·배포·타인에게 메시지 전송을 하지 않는다. 필요하지 않은 외부 서비스 설치를 완료의 선행 조건으로 만들지 않는다.
- 시간/토큰이 부족하거나 연구 결과가 실패했다고 완료로 표시하지 않는다. 중단 시 달성/미달성/막힌 조건과 바로 재개할 지점을 정확히 남긴다.
- 모든 기능을 임의의 자연어·모든 지식에서 일반적으로 해결했다는 뜻으로 확대하지 않는다. 종료점은 **Addition의 명시된 완료 기준을 공통 코어와 실행 가능한 ALMA 0.1에서 충족하고, 정확성·근거·재시작·학습 효과를 검증한 상태**다.

최종 보고에는 각 완료 기준의 상태와 연결된 코드·시험·원시 결과, 두 영역의 이전 goal 마감 증거, 네 영역의 전이, 학습/압축/감정/선호의 전후 비교, 실제 관찰된 milestone, 코드·팩·자료 식별 정보, 비용, 남은 제한을 포함한다. 검증하지 못한 항목은 분명히 미완료로 남긴다.
